1  Introducción

Este documento constituye la Especificación de Requisitos de Software (SRS) del sistema Step & Style, una plataforma de comercio electrónico de calzado. Se describen el comportamiento esperado del sistema, sus funcionalidades y las restricciones bajo las cuales debe operar, siguiendo el estándar IEEE Std 830-1998.

1.1  Propósito

El propósito de este documento es describir de manera completa y precisa los requisitos funcionales y no funcionales del sistema Step & Style.

Está dirigido a:

  • El equipo de desarrollo (Grupo 9), como guía de implementación.
  • Docentes evaluadores, como instrumento de validación del proyecto.

1.2  Alcance

Step & Style es una plataforma de e-commerce de calzado desarrollada como proyecto académico. Permite a clientes explorar y comprar productos, y a administradores gestionar el catálogo, los usuarios y los pedidos.

El sistema cubre:

  • Catálogo público de productos con filtros por categoría, precio y talle.
  • Registro, autenticación y recuperación de contraseña de usuarios.
  • Carrito de compras y proceso de pago con múltiples métodos.
  • Generación de factura digital por compra.
  • Notificaciones de reingreso de stock.
  • Panel de administración para productos, usuarios, pedidos y configuración de precios.

Queda fuera del alcance: integración real con pasarelas de pago externas (los pagos son simulados), envíos físicos y facturación electrónica fiscal.

2  Descripción general

2.1  Perspectiva del producto

Step & Style es un sistema independiente de comercio electrónico orientado a la venta minorista de calzado. No forma parte de un sistema mayor preexistente.

El sistema se compone de:

  • Una interfaz pública (frontend) accesible por cualquier visitante.
  • Un panel de cliente para usuarios registrados.
  • Un panel de administración exclusivo para administradores.
  • Una base de datos relacional (MariaDB) como capa de persistencia.
  • Un servidor web local (Laravel Herd o equivalente) como entorno de ejecución.

2.2  Funcionalidad del producto

Para visitantes (sin autenticación):

  • Navegar el catálogo con filtros por categoría, precio y talle.
  • Ver el detalle de cada producto.
  • Registrarse o iniciar sesión.
  • Recuperar contraseña por correo electrónico.
  • Enviar consultas a través del formulario de contacto.

Para clientes autenticados:

  • Gestionar el carrito (agregar, modificar cantidad, eliminar ítems).
  • Realizar compras con cuatro métodos de pago: débito, crédito con cuotas, transferencia bancaria y MercadoPago.
  • Consultar historial de compras con filtros.
  • Ver y descargar la factura de cada pedido.
  • Suscribirse a notificaciones de reingreso de stock.
  • Editar datos personales.

Para administradores:

  • Dashboard con métricas del sistema.
  • Gestión completa de productos (crear, editar, activar/inactivar, restaurar, eliminar definitivamente).
  • Gestión de usuarios con filtros, cambio de rol, activación/inactivación y edición de datos.
  • Seguimiento y actualización de estado de pedidos.
  • Configurar porcentajes de descuento y recargo por método de pago.
  • Ver el carrito actual de cualquier cliente.

2.4  Restricciones

  • El sistema debe ejecutarse sobre PHP 8.4 y Laravel 13.
  • La base de datos debe ser MariaDB (o MySQL compatible).
  • El entorno de desarrollo es local; no está previsto despliegue en producción en la nube.
  • Los pagos son simulados; no se integra con pasarelas reales.
  • El sistema usa soft delete para usuarios y productos.
  • La autenticación es exclusivamente por email y contraseña.
  • Las imágenes de productos se almacenan en el sistema de archivos local del servidor.

2.5  Suposiciones y dependencias

  • Se asume que cada instalador dispone de PHP 8.4, Composer y MariaDB operativos.
  • El archivo .sql de la base de datos debe importarse manualmente antes del primer uso.
  • El servidor de correo debe estar configurado en el .env para la recuperación de contraseña.
  • El sistema depende de Bootstrap 5 (CDN); requiere conexión a internet para cargarlo en desarrollo.

2.6  Evolución previsible del sistema

  • Integración con la API real de MercadoPago.
  • Sistema de reseñas y calificaciones de productos.
  • Envío de facturas por correo electrónico al cliente.
  • Módulo de reportes y estadísticas de ventas con gráficos.
  • Internacionalización (soporte multi-idioma).
  • Despliegue en servidor en la nube.

3  Requisitos específicos

Los requisitos se identifican con el formato RF-XX (funcionales) y RNF-XX (no funcionales). Para cada requisito se indica número, nombre, tipo, fuente, prioridad y descripción.

3.1  Requisitos comunes de los interfaces

3.1.1  Interfaces de usuario

El sistema provee una interfaz web accesible desde cualquier navegador moderno, con diseño responsivo basado en Bootstrap 5:

  • En pantallas grandes (≥ 1200px): tablas de datos.
  • En pantallas pequeñas (< 1200px): tarjetas (cards).

Las acciones críticas (inactivar usuario, eliminar producto) requieren confirmación mediante modales.

3.1.2  Interfaces de hardware

No se requiere hardware específico más allá de un equipo con procesador compatible con PHP 8.4, memoria RAM suficiente para un servidor web local y conexión de red local.

3.1.4  Interfaces de comunicación

  • Comunicación vía HTTP/HTTPS con rutas web de Laravel.
  • Formularios protegidos con tokens CSRF.
  • Envío de correos mediante el sistema de Mail de Laravel (SMTP configurable o driver log).
  • No se expone ninguna API REST pública en la versión actual.

3.2  Requisitos funcionales

RF-01 — Registro de usuario

Número de requisitoRF-01
Nombre de requisitoRegistro de usuario
TipoRequisito
Fuente del requisitoVisitante
Prioridad del requisitoAlta / Esencial

El sistema debe permitir que un visitante cree una cuenta proporcionando nombre, email y contraseña. El email debe ser único en el sistema. La contraseña se almacena hasheada con bcrypt. Al registrarse, el usuario recibe el rol "cliente" automáticamente.

RF-02 — Inicio de sesión

Número de requisitoRF-02
Nombre de requisitoInicio de sesión
TipoRequisito
Fuente del requisitoCliente / Admin
Prioridad del requisitoAlta / Esencial

El sistema debe autenticar usuarios mediante email y contraseña. Si las credenciales son correctas, redirige al panel correspondiente según el rol (cliente → /cliente, admin → /admin). Si son incorrectas, muestra un mensaje de error sin revelar cuál campo falló.

RF-03 — Recuperación de contraseña

Número de requisitoRF-03
Nombre de requisitoRecuperación de contraseña
TipoRequisito
Fuente del requisitoCliente / Admin
Prioridad del requisitoAlta / Esencial

El sistema debe permitir restablecer la contraseña mediante un enlace enviado al email registrado. El enlace tiene vigencia limitada. El usuario puede ingresar y confirmar una nueva contraseña en /reset-password/{token}.

RF-04 — Cierre de sesión

Número de requisitoRF-04
Nombre de requisitoCierre de sesión
TipoRequisito
Fuente del requisitoCliente / Admin
Prioridad del requisitoAlta / Esencial

El sistema debe permitir al usuario autenticado cerrar su sesión desde cualquier página del sitio, invalidando la sesión activa.

RF-05 — Catálogo de productos público

Número de requisitoRF-05
Nombre de requisitoCatálogo público de productos
TipoRequisito
Fuente del requisitoVisitante / Cliente
Prioridad del requisitoAlta / Esencial

El sistema debe mostrar en la página principal (/) todos los productos activos con imagen, nombre, precio y categoría. Debe permitir filtrar por categoría (botas, sandalias, zapatos), precio mínimo, precio máximo y talle disponible, y ordenar por precio ascendente o descendente.

RF-06 — Detalle de producto

Número de requisitoRF-06
Nombre de requisitoVista de detalle de producto
TipoRequisito
Fuente del requisitoVisitante / Cliente
Prioridad del requisitoAlta / Esencial

El sistema debe mostrar la información completa de un producto: nombre, descripción, categoría, precio, imagen y talles disponibles con su stock. Si un talle tiene stock 0, debe mostrarse como no disponible.

RF-07 — Gestión del carrito de compras

Número de requisitoRF-07
Nombre de requisitoCarrito de compras
TipoRequisito
Fuente del requisitoCliente
Prioridad del requisitoAlta / Esencial

El sistema debe permitir al cliente autenticado:

  • Agregar un producto seleccionando talle y cantidad.
  • Ver el carrito con todos los ítems, precios unitarios y totales.
  • Modificar la cantidad de un ítem.
  • Eliminar un ítem del carrito.
  • Ver el subtotal actualizado.

RF-08 — Proceso de pago

Número de requisitoRF-08
Nombre de requisitoProceso de pago
TipoRequisito
Fuente del requisitoCliente
Prioridad del requisitoAlta / Esencial

El sistema debe permitir al cliente confirmar la compra seleccionando un método de pago:

  • Débito: número de tarjeta (16 dígitos), nombre del titular, fecha de vencimiento y CVV.
  • Crédito: ídem débito, más selección de cuotas (3, 6, 9 o 12). Aplica recargo configurable.
  • Transferencia bancaria: número de operación de 6 dígitos.
  • MercadoPago: número de operación de 6 dígitos. Aplica descuento configurable.

El sistema debe validar que la tarjeta no esté vencida. El pago se procesa en una transacción de base de datos con bloqueo de fila (lockForUpdate) que verifica y descuenta el stock. Si el stock es insuficiente, se cancela la operación y se informa al cliente.

RF-09 — Generación de factura

Número de requisitoRF-09
Nombre de requisitoFactura de compra
TipoRequisito
Fuente del requisitoCliente
Prioridad del requisitoAlta / Esencial

Al confirmar el pago, el sistema debe generar un pedido con número de factura único (formato FAC-XXXXXXXX) y redirigir al cliente a la vista de factura, mostrando: ítems comprados, subtotal, descuento o recargo aplicado y total final.

RF-10 — Historial de compras

Número de requisitoRF-10
Nombre de requisitoHistorial de compras del cliente
TipoRequisito
Fuente del requisitoCliente
Prioridad del requisitoAlta / Esencial

El sistema debe permitir al cliente ver todos sus pedidos ordenados por fecha descendente, con filtros por método de pago, estado y rango de fechas. Desde el historial debe acceder a la factura de cada pedido.

RF-11 — Notificación de reingreso de stock

Número de requisitoRF-11
Nombre de requisitoSuscripción a notificación de stock
TipoRequisito
Fuente del requisitoCliente

  • Editar todos los campos de un producto existente.
  • Inactivar un producto (soft delete): deja de mostrarse en el catálogo público.

  • Eliminar definitivamente un producto (force delete).
  • Gestionar los talles y el stock por talle de cada producto.

3.3  Requisitos no funcionales

3.3.1  Requisitos de rendimiento

Número de requisitoRNF-01
Nombre de requisitoRendimiento de respuesta
TipoRestricción
Prioridad del requisitoMedia / Deseado

El sistema debe responder a las solicitudes del usuario en menos de 3 segundos en condiciones normales de uso (entorno local, un usuario concurrente). Las consultas a la base de datos deben estar optimizadas mediante eager loading (with()) de Eloquent.

3.3.2  Seguridad

Número de requisitoRNF-02
Nombre de requisitoSeguridad del sistema
TipoRestricción
Prioridad del requisitoAlta / Esencial
  • Las contraseñas se almacenan con hash bcrypt.
  • Todos los formularios están protegidos con tokens CSRF.
  • El acceso al panel de administración está restringido por rol; sin autorización devuelve HTTP 403.
  • Las rutas de cliente están protegidas con el middleware auth.
  • Los datos de tarjeta no se almacenan en la base de datos.
  • Las transacciones de compra usan lockForUpdate para evitar condiciones de carrera en el stock.
  • La inactivación de un usuario admin requiere verificación adicional de contraseña.

3.3.3  Fiabilidad

Número de requisitoRNF-03
Nombre de requisitoFiabilidad en el proceso de compra
TipoRestricción
Prioridad del requisitoAlta / Esencial

El proceso de compra se ejecuta dentro de una transacción de base de datos (DB::transaction). Si ocurre cualquier error (stock insuficiente, fallo de escritura), la transacción se revierte completamente, garantizando la integridad de los datos.

3.3.4  Disponibilidad

Número de requisitoRNF-04
Nombre de requisitoDisponibilidad en entorno local
TipoRestricción
Prioridad del requisitoMedia / Deseado

El sistema debe estar disponible durante el horario de uso académico y de evaluación. Al tratarse de un entorno local, la disponibilidad depende del equipo del desarrollador. No se define un SLA de uptime para esta etapa del proyecto.

3.3.5  Mantenibilidad

Número de requisitoRNF-05
Nombre de requisitoMantenibilidad del código
TipoRestricción
Prioridad del requisitoMedia / Deseado
  • El sistema sigue la arquitectura MVC de Laravel.
  • La lógica de configuración de precios está centralizada en ConfiguracionService.
  • El uso de soft deletes permite recuperar datos sin intervención directa en la base de datos.

3.3.6  Portabilidad

Número de requisitoRNF-06
Nombre de requisitoPortabilidad del entorno de desarrollo
TipoRestricción
Prioridad del requisitoMedia / Deseado
  • El sistema puede ejecutarse en Windows, macOS o Linux con PHP 8.4 y MariaDB.
  • Las dependencias se gestionan exclusivamente mediante Composer.
  • La configuración del entorno está aislada en el archivo .env.

3.4  Otros requisitos

Requisitos de interfaz visual: coherencia Bootstrap 5 en todas las vistas (frontend y panel de administración).

Requisitos de datos iniciales: el sistema requiere importar grupo9.sql antes del primer uso.

Requisitos de accesibilidad: las páginas deben funcionar en Chrome, Firefox, Edge y Safari (versiones actuales).
